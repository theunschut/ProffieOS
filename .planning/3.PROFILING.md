## Frame Rate Measurement Methodology

### Environment Setup
- **Hardware Target:** ESP32-based Proffieboard (estimated 100 LEDs)
- **FPS Target:** 60 FPS nominal
- **Frame Time Budget:** ~16.67 ms per frame
- **Measurement Tools:**
  - `micros()` timestamps for precise timing
  - Serial output logging for frame counts
  - Statistical analysis of variance

### Test Styles
1. **test_simple.style** - Minimal baseline
   - Layers<Blue, AlphaL<Black, InOutHelperF<InOutFunc<300, 800>>>>
   - Components: 1 layer, 1 alpha transition, 2 functions
   - Use case: Measure baseline overhead

2. **assassin.style** - Complex test case
   - Full effects: flicker, swing ripple, lockup, clash, blast, stab
   - Components: 10+ layers, multiple effects
   - Use case: Measure worst-case performance

### Measurement Protocol

**Baseline (Pre-Fix):**
- Record frame times for 100+ consecutive frames
- Calculate mean, std dev, min/max
- Identify dropped frames (>20ms) and stutter

**Post-Fix Validation:**
- Repeat same measurement sequence
- Compare: baseline vs post-fix
- Calculate variance: `(post - baseline) / baseline * 100%`
- Accept if variance < 5% or document as limitation

### Performance Baseline Reference

**Frame Time Budget (100 LEDs @ 60 FPS):**
- Total per-frame time: ~16.67 ms (1000 ms / 60 FPS)
- Blade LED updates: ~6-8 ms (100 LEDs × getColor() calls)
- ProffieOS overhead: ~8-10 ms
- Style functions: <1 ms (must be efficient)

**Virtual Dispatch Overhead:**
- Estimated from Phase 1: ~1% frame rate impact
- Acceptable if within 5% of compiled equivalent

## Current State Analysis

### RtIgnitionDelay Implementation
**Location:** sd_style.h lines 1914-1928

```cpp
class RtIgnitionDelay : public RtColorNode, public IgnitionDelayBase<RtFuncAdapter> {
  using Base = IgnitionDelayBase<RtFuncAdapter>;
public:
  RtIgnitionDelay(RtFuncNode* ms, RtColorNode* base) : base_(base) {
    millis_.f_.node_ = ms;
  }
  ~RtIgnitionDelay() override { delete millis_.f_.node_; delete base_; }
  void run(BladeBase* blade) override {
    Base::run(blade);   // runs millis_, updates delay state, sets blade_
    base_->run(this);   // child sees delayed is_on() via this BladeWrapper
  }
  RGBA_um getColor(int led) override { return base_->getColor(led); }
private:
  RtColorNode* base_;
};
```

**Analysis:**
- Uses `IgnitionDelayBase<RtFuncAdapter>` for state management
- `run()` called every frame - expected behavior
- No visible timing bug in this class directly
- Issue likely in: IgnitionDelayBase timing logic or state initialization

### RtInOutHelperF Implementation
**Location:** sd_style.h lines 314-325

```cpp
class RtInOutHelperF : public RtFuncNode, public InOutHelperFBase {
public:
  explicit RtInOutHelperF(RtFuncNode* ext, bool /*allow_disable*/ = true) : ext_(ext) {}
  ~RtInOutHelperF() override { delete ext_; }
  void run(BladeBase* blade) override {
    ext_->run(blade);
    thres = ext_->getInteger(0) * blade->num_leds() - 32768;
  }
  int getInteger(int led) override { return InOutHelperFBase::getInteger(led); }
private:
  RtFuncNode* ext_;
};
```

**Analysis:**
- Inherits InOutHelperFBase for per-LED wipe math
- Computes threshold each frame: `thres = ext value * num_leds - 32768`
- Should be fast (single multiply + subtract)
- InOutHelperFBase::getInteger() computes wipe position per LED

## Known Issues to Investigate

### Issue 1: Fast Ignition Regression
**Symptom:** Ignition animation appears slow or stuttering

**Priority Investigation:**
1. Check if RtIgnitionDelay::run() called every frame (add frame counter)
2. Check timer state initialization (when does delay start counting?)
3. Check timer increment logic in IgnitionDelayBase (millisecond calculation correct?)
4. Compare IgnitionDelayBase behavior vs compiled equivalent

**Hypothesis:** Timer not updating correctly each frame, or delay value misinterpreted

### Issue 2: Pre-Ignited Color
**Symptom:** Blade shows color before ignition event

**Priority Investigation:**
1. Trace color initialization in RtAlphaL::getColor()
2. Check if blade state is available (blade pointer, is_on() method)
3. Check if blade state checked before returning color
4. Load greyscale font test and observe pre-ignition behavior

**Hypothesis:** Color returned without checking ignition state

### Issue 3: Missing Effects Parsing
**Symptom:** Some effect tokens fail to parse

**Priority Investigation:**
1. Audit parser sections (30+ headers documented in Phase 2)
2. Create test styles for each documented effect
3. Parse and check: Is token recognized or logged as unknown?
4. Identify coverage gaps and missing Rt* implementations

**Hypothesis:** Parser gaps in effect tokens or missing Rt* wrappers

### Issue 4: Return Value Semantics
**Symptom:** Blade stays powered when should turn off

**Priority Investigation:**
1. Check RtColorNode::run() signature (returns void!)
2. Check RtFuncNode::run() signature (returns void!)
3. No mechanism to signal "blade can power down"
4. Need to add return value semantic (bool or separate method)

**Hypothesis:** run() returns void, no power control propagation
