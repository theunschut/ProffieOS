## Issue #1: Fast Ignition Regression

### Symptom
Ignition animation appears slow or stuttering when loaded from SD card, compared to compiled equivalent.

### Root Cause Possibilities (in priority order)

**Priority 1: Timer Not Updating Correctly** (Highest Probability)
- **How to detect:** Add frame counter debug output to RtIgnitionDelay::run()
- **Investigation:**
  ```cpp
  // In RtIgnitionDelay::run(), add:
  static int frame_count = 0;
  STDOUT.print("Frame ");
  STDOUT.println(frame_count++);
  // If no output, run() not being called each frame — critical issue
  ```
- **What to check:**
  1. Is RtIgnitionDelay::run() being called every frame?
  2. Is timer state initialized when ignition triggers?
  3. Is timer increment logic correct (micros(), timestamps, accumulation)?
  4. Is there a reset logic that wrongly resets timer mid-animation?

**Priority 2: Delay Value Wrong** (Medium Probability)
- **How to detect:** Log delay_ms_ and compare to expected (should match Ignition token parameter)
- **Investigation:**
  - Does parser pass correct delay value?
  - Does IgnitionDelayBase expect delay in ms or different units?
  - Check: Is delay 300ms, or being interpreted as 300 frames?

**Priority 3: Virtual Dispatch Overhead** (Lower Probability)
- **How to detect:** Not a code bug, but performance characteristic
- **Mitigation:** If detected via profiling, add `__attribute__((always_inline))` hints
- **Note:** Phase 1 estimated ~1% frame rate impact (acceptable)

**Priority 4: State Machine Logic** (Lower Probability)
- **How to detect:** Compare state transitions in IgnitionDelayBase vs RtIgnitionDelay
- **Investigation:**
  - Does IgnitionDelayBase have states (pre-delay, animating, post-delay)?
  - Are states transitioning correctly?
  - Is there a bug where state gets stuck?

### Investigation Checklist

- [ ] Locate RtIgnitionDelay class (search "RtIgnitionDelay" in sd_style.h)
- [ ] Locate IgnitionDelayBase (should be included from ignition_delay.h, line 37)
- [ ] Add debug output to RtIgnitionDelay::run() (frame counter, timer value, state)
- [ ] Load test style with ignition, observe debug output
- [ ] Compare timing: expected vs actual (use frame count × frame time)
- [ ] Compare with compiled StylePtr equivalent on same hardware
- [ ] Profile with "top" command if available (identify CPU hotspot)

### Code Pattern: Correct Ignition Timer

From other timer-based classes (RtSlowNoise, RtSin), the pattern should be:

```cpp
class RtIgnitionDelay : public RtColorNode, public IgnitionDelayBase {
public:
  void run(BladeBase* blade) override {
    uint32_t now = micros();
    if (!started_) {
      start_time_ = now;
      started_ = true;
    }
    uint32_t elapsed_us = now - start_time_;
    // Call base class run() with elapsed time
    IgnitionDelayBase::run(blade, elapsed_us / 1000);  // convert to ms
  }
private:
  uint32_t start_time_ = 0;
  bool started_ = false;
};
```

### Performance Baseline Reference

**Frame Time Budget (100 LEDs @ 60 FPS):**
- Total per-frame time: ~16.67 ms
- Blade LED updates: ~6 ms (100 LEDs × getColor() calls)
- ProffieOS overhead: ~10 ms
- Style functions (RtIgnitionDelay, etc.): <1 ms (must be efficient)

**Success Threshold:**
- Ignition animation speed within 10% of compiled equivalent
- Frame rate maintains 60 FPS during animation
- No visible stutter or dropped frames

## Issue #2: Pre-Ignited Color

### Symptom
Blade shows color when should be dark (before ignition event triggers).
Often affects greyscale fonts or styles without explicit black initialization.

### Root Cause Possibilities (in priority order)

**Priority 1: Color Returned Without Checking Ignition State** (Highest Probability)
- **How to detect:** Add check in RtAlphaL or root color node
- **Investigation:**
  ```cpp
  // In RtAlphaL::getColor(), check if blade should be on:
  RGBA_um getColor(int led) override {
    if (!blade_->is_on()) {
      STDOUT.println("Pre-ignition: blade off, returning transparent");
      return RGBA_um::Transparent();
    }
    return Base::getColor(led);
  }
  ```
- **What to check:**
  1. Is blade state available? (blade_ pointer should be passed to getColor()?)
  2. What's the correct way to check ignition state in ProffieOS?
  3. Should check happen at root node (RtCompose) or leaf (RtAlphaL)?

**Priority 2: Default Color Value Wrong** (Medium Probability)
- **How to detect:** Check what color is returned before ignition
- **Investigation:**
  - Is default color black or something else?
  - Does initialization set color to "off" state?
  - Check RtRgb, RtRgba default values

**Priority 3: Alpha Channel Not Handled** (Medium Probability)
- **How to detect:** Color appears at full opacity when should be transparent
- **Investigation:**
  - RGBA_um has alpha component (0 = transparent, 32768 = opaque)
  - Is alpha being set to 0 before ignition?
  - Check RtAlphaL alpha function (should it return 0 pre-ignition?)

**Priority 4: Initialization Order Issue** (Lower Probability)
- **How to detect:** Color correct after first frame, but wrong on first frame
- **Investigation:**
  - Does run() get called before getColor()?
  - Is state initialized before first color read?
  - Check: initialization in constructor vs first run() call

### Investigation Checklist

- [ ] Reproduce issue: Load style with known pre-ignition, verify it shows color
- [ ] Add debug output in RtAlphaL::getColor() to log returned color
- [ ] Check blade state API: blade->is_on(), SaberBase::IsOn(), or other?
- [ ] Trace: When does blade transition from "off" to "on"?
- [ ] Verify: Alpha function returning 0 before ignition (or not?)
- [ ] Test on greyscale font specifically
- [ ] Compare with compiled StylePtr equivalent (what's it doing?)

### Code Pattern: Correct Ignition-Aware Color

```cpp
class RtAlphaL : public RtColorNode, public AlphaL<RtColorAdapter, RtFuncAdapter> {
  using Base = AlphaL<RtColorAdapter, RtFuncAdapter>;
public:
  RtAlphaL(RtColorNode* color, RtFuncNode* alpha) { color_.node_ = color; alpha_.node_ = alpha; }
  ~RtAlphaL() override { delete color_.node_; delete alpha_.node_; }
  void run(BladeBase* blade) override { Base::run(blade); }
  RGBA_um getColor(int led) override {
    // Option 1: Check blade state directly
    if (!blade_->is_on()) {  // Assumes blade_ is member variable
      return RGBA_um::Transparent();
    }
    return Base::getColor(led);
  }
private:
  BladeBase* blade_;  // Need to store blade reference
};
```

### Initialization State Flow

**Expected sequence:**
1. Style parsed, tree created
2. run() called each frame with blade pointer
3. getColor() called after run()
4. Blade state checked: is_on() == false initially
5. Color returned: Transparent or Black
6. Ignition triggered: blade state transitions to on
7. Subsequent getColor() returns actual color

**Problem:** If step 5 returns non-transparent color despite is_on() == false, that's the bug.

## Issue #3: Missing Effects Parsing

### Symptom
Styles with certain effect tokens fail to parse or parse incorrectly.
Unknown tokens degrade gracefully (log warning, substitute Black), so issue is "wrong effect rendered" or "parse error" not crash.

### Root Cause Possibilities (in priority order)

**Priority 1: Parser Token Not Matched** (Highest Probability)
- **How to detect:** Add debug output to parser, try parsing each effect token
- **Investigation:**
  1. List all documented ProffieOS effects (see REQUIREMENTS.md FR1.2)
  2. For each effect: Create minimal test style with just that effect
  3. Parse and check: Is it recognized or logged as unknown?
  4. Effects to test: AudioFlicker, HumpFlicker, RandomFlicker, Strobe, Pulsing, Clash, Stab, Lockup, Blast, etc.

**Priority 2: Parser Token Matched But Rt* Implementation Missing** (Medium Probability)
- **How to detect:** Token recognized, but Rt* class doesn't exist
- **Investigation:**
  - Parser has `if (!strcmp(token, "Effect"))` but no `new RtEffect(...)`
  - Solution: Implement Rt* wrapper for the effect

**Priority 3: Parser Token Matched But Arguments Wrong** (Medium Probability)
- **How to detect:** Token recognized, but effect renders wrong
- **Investigation:**
  - Parser matches token but passes wrong args to Rt* class
  - Example: Token has 3 args, parser only passes 2
  - Solution: Fix parser argument extraction

**Priority 4: Effect Consolidation Incomplete** (Lower Probability)
- **How to detect:** Multiple similar effects (flicker variants) in parser
- **Investigation:**
  - Phase 2 consolidated flicker variants using make_flicker lambda
  - Check: Is consolidation working or did we miss some variants?
  - Compare: All expected flicker types covered?

### Investigation Checklist

- [ ] Create EFFECT_COVERAGE.md table (effect name vs parser status)
- [ ] For each documented effect: Create minimal test style
- [ ] Parse each test style: Record success/failure
- [ ] For failures: Determine if token not matched or Rt* not implemented
- [ ] Check parser sections: Are all documented effects in parser?
- [ ] Cross-reference: REQUIREMENTS.md FR1.2 vs parser tokens
- [ ] Test: Effect produces correct visual output (if possible)

### Parser Structure Reference

**Main parser sections (from Phase 2 notes, 30+ headers):**
1. Layer composition (Layers, AlphaL, Mix)
2. Stripes and patterns (Stripes, HardStripes, RotateColors)
3. Transitions (InOutHelper, InOutSparkTip, Transition effects)
4. Flicker effects (AudioFlicker, BrownNoiseFlicker, HumpFlicker, RandomFlicker, Strobe, Pulsing)

## Issue #4: Return Value Semantics (Power Control)

### Symptom
Blade stays powered when should turn off after effect ends.
Likely causes battery drain because LED stays on even when animation is done.

### Root Cause Possibilities (in priority order)

**Priority 1: Return Type is void, Not bool** (Highest Probability)
- **How to detect:** Check RtColorNode and RtFuncNode base classes
- **Investigation:**
  ```cpp
  class RtColorNode {
  public:
    virtual void run(BladeBase* blade) = 0;  // RETURNS VOID!
    virtual RGBA_um getColor(int led) = 0;
  };
  ```
- **Issue:** No mechanism to signal "blade can power down"
- **Solution:** Change run() to return bool (or add separate method)

**Priority 2: No Propagation of Power Control Through Tree** (High Probability)
- **How to detect:** Even if run() returns bool, is it used by parent nodes?
- **Investigation:**
  - RtCompose has base and layer — which determines power state?
  - RtMix has function and two colors — what's power state?
  - Should it be: "power off only if all components agree"?

**Priority 3: Effect Duration Logic Missing** (Medium Probability)
- **How to detect:** Effect never signals "done" to power control
- **Investigation:**
  - Effects like Blast, Clash have duration (fade time)
  - When fade completes, should run() return false?
  - Check: RtBlastF, RtLocalizedClashF have timing logic?

**Priority 4: Default Power State Wrong** (Lower Probability)
- **How to detect:** All styles, default power state is "keep powered"
- **Investigation:**
  - Should default be true (keep on) or false (can power off)?
  - If default true, styles that should turn off won't
  - Verify assumption with ProffieOS documentation

### Investigation Checklist

- [ ] Search for BladeStyle::run() in blade_style.h (see return type contract)
- [ ] Check how compiled styles propagate power control (inheritance chain)
- [ ] Verify: What does run() return value mean? (true = on, false = off, or opposite?)
- [ ] Audit RtColorNode::run() and RtFuncNode::run() — change to bool?
- [ ] Update all Rt* implementations — handle bool return
- [ ] Test: Load effect style, verify blade powers off when expected
- [ ] Compare: vs compiled StylePtr (power-off timing should match)

### Code Pattern: Power Control Return Value

**Option A: Change run() signature to return bool**

```cpp
// Base classes
class RtColorNode {
public:
  virtual bool run(BladeBase* blade) = 0;  // true = keep powered, false = can power off
  virtual RGBA_um getColor(int led) = 0;
};

// Composition
class RtCompose : public RtColorNode {
public:
  bool run(BladeBase* blade) override {
    bool base_power = base_->run(blade);
    bool layer_power = layer_->run(blade);
    return base_power || layer_power;  // Stay on if either component says so
  }
};

// Effect with duration
class RtBlastF : public RtFuncNode {
public:
  bool run(BladeBase* blade) override {
    // ... update state ...
    // Return true while effect is active, false when faded out
    return fade_magnitude > 0;
  }
};
```

**Option B: Add separate canPowerOff() method**

```cpp
class RtColorNode {
public:
  virtual void run(BladeBase* blade) = 0;  // Keep as void
  virtual RGBA_um getColor(int led) = 0;
  virtual bool canPowerOff() { return true; }  // Default: can power off
};

class RtBlastF : public RtFuncNode {
public:
  bool canPowerOff() override {
    return fade_magnitude <= 0;  // Power off when faded out
  }
};
```

**Option C: Store power state in node**

```cpp
class RtColorNode {
public:
  virtual void run(BladeBase* blade) = 0;
  virtual RGBA_um getColor(int led) = 0;
  bool should_stay_powered() const { return power_state_; }
protected:
  bool power_state_ = false;  // Default: can power off
};

class RtBlastF : public RtFuncNode {
public:
  void run(BladeBase* blade) override {
    // ... update state ...
    power_state_ = (fade_magnitude > 0);
  }
};
```

### Power Control State Machine

**Expected behavior:**
1. Style loaded, nodes created
2. run() called each frame
3. run() updates internal state based on blade events (ignition, effects)
4. run() or canPowerOff() signals: "blade can power down"
5. BladeStyle checks: If all effects say "can power off", blade powers down
6. Result: Blade only stays powered while effects active

**Test case:**
```
Timeline:
  T=0ms: Ignition triggered
  T=0-300ms: Ignition fade in (run returns true = stay powered)
  T=300-1000ms: Blade stable (run returns false or canPowerOff = true)
  T=1000ms: Clash effect
  T=1000-1500ms: Clash effect active (run returns true)
  T=1500ms: Clash effect ends
  T=1500+: run returns false, blade powers off

Result: Blade on 1500ms total (0-300 + 1000-1500)
```
