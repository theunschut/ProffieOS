### Task 1.3: Analyze Template Composition Patterns (0.5h)

**Objective:** Understand how templates compose and how adapters enable this at runtime

**Actions:**
1. Study template wrapper examples:
   - **AlphaL<COLOR, ALPHA_FUNC>**: Takes color and function templates
     - Current sd_style.h: RtAlphaL inherits from AlphaL<RtColorAdapter, RtFuncAdapter>
     - Question: Is this inheritance correct? Should it be composition?

   - **Mix<F, A, B>**: Binary color mixer with function F and color operands A, B
     - Current: RtMix manually reimplements mixing logic
     - Alternative: wrap Mix<RtFuncAdapter, RtColorAdapter, RtColorAdapter>?

   - **Stripes<WIDTH, SPEED, COLORS...>**: Color stripe pattern
     - Variadic templates—hard to handle at runtime
     - Current: RtHardStripes reimplements directly
     - Design: Is wrapper feasible, or accept reimplementation?

   - **InOutSparkTipX<COLOR, FUNCTION>**: Spark at wipe boundary
     - Current: RtInOutSparkTipX wraps via InOutSparkTipX<RtColorAdapter, RtFuncAdapter>
     - Pattern: Works well—is this the template wrapper pattern profezzorn recommended?

   - **Ifon<ON_VAL, OFF_VAL>**: Conditional function
     - Pattern: Reuse via Ifon<RtFuncAdapter, RtFuncAdapter>?

2. Document the **Adapter Pattern**:
   ```cpp
   struct RtColorAdapter {
     RtColorNode* ptr;
     auto getColor(int led) { return ptr->getColor(led); }
     // Satisfies template parameter of AlphaL<COLOR, ...>
   };
   ```
   - Why does this work? (Duck typing, no virtual required in template)
   - Limitations? (Can't infer types at runtime, getColor() return type is RGBA_um)
   - Performance? (One virtual call per adapter invocation, acceptable)

3. Categorize template types:
   - **Hard to wrap** (variadic composition): Layers, Stripes, Mix with many operands
   - **Easy to wrap** (fixed template params): AlphaL, InOutSparkTipX, Ifon, Bump, SmoothStep
   - **Trivial to reimplement**: Const colors, simple transforms (Scale, Compose)

4. Create `.planning/codebase/TEMPLATE_PATTERNS.md` with examples and wrapping feasibility

**Success Criteria:**
- [ ] Adapter pattern fully understood
- [ ] Template categories identified
- [ ] Wrapping feasibility assessed for 20+ templates

### Task 1.6: Create Architecture Decision Record (ADR) (0.5h)

**Objective:** Document key decisions for future reference and code review

**Actions:**
1. Create `.planning/codebase/ADR_TEMPLATE_WRAPPER.md`:

```markdown
# ADR: Use Adapter Pattern for Template Wrapping

## Context
ProffieOS uses compile-time template composition for zero-cost style assembly.
Runtime style loading requires dynamic dispatch (virtual functions).
Profezzorn recommended template wrapping instead of full reimplementation.

## Decision
Use **adapter pattern** with RtColorAdapter/RtFuncAdapter pointers to satisfy
template parameters, enabling reuse of templates like AlphaL, Ifon, InOutSparkTipX.

### Example
```cpp
class RtAlphaL : public AlphaL<RtColorAdapter, RtFuncAdapter> {
  // Inherits from compiled template
  // RtColorAdapter/RtFuncAdapter dispatch to Rt* nodes
};
```

## Rationale
- **Reuse**: No reimplementation of AlphaL logic
- **Type safety**: Template still type-checked at compile
- **Perf**: One virtual call per color/function reference (acceptable for ~300k calls/sec)
- **Simplicity**: Duck typing in templates, explicit pointers at runtime

## Consequences
- Positive: Reduced code duplication, improved maintainability
- Negative: Virtual dispatch adds ~1 cycle per call
- Neutral: Requires understanding of both compile and runtime type systems

## Alternatives Considered
1. Full reimplementation (current state): Works but duplicates code
2. Template metaprogramming at runtime: Not feasible (templates resolved at compile)
3. Code generation: Overkill for this use case

## Status
**PROPOSED** - Pending Phase 1 design review and Phase 2 implementation validation
```

2. Create additional ADRs as needed:
   - ADR: Variadic Pattern Handling (why Layers/Stripes stay reimplemented)
   - ADR: Parser Strategy (recursive descent vs other)
