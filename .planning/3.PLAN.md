# Phase 3: Debug & Fix Known Issues

**Phase Goal:** Debug and fix known issues preventing runtime style parsing from working correctly, enabling production-ready SD-card style loading.

**Expected Duration:** 6-8 hours
**Branch:** feature/StyleFromSD
**Starting State:** 4,259 lines, 108 classes, well-organized parser with 30+ section headers

---

## Known Issues Overview

From Phase 2 Architecture Overview (sd_style.h lines 73-77):

1. **Fast ignition regression** — Ignition transition showing wrong timing
   - Hypothesis: Extra virtual dispatch overhead vs compiled
   - Impact: Ignition animation appears slow or stuttering

2. **Pre-ignited color** — Some blade styles show color before ignition event
   - Hypothesis: Color initialization not respecting ignition state
   - Impact: Blade shows color when it should be dark

3. **Missing effects parsing** — Some effect tokens may not parse completely
   - Hypothesis: Parser coverage gaps in effect/transition section
   - Impact: Styles with certain effects fail silently or degrade

4. **Return value semantics** — run() return values need validation for power control
   - Hypothesis: Blade can't power down because run() returns true when should be false
   - Impact: Blade stays powered after effects end (drains battery)

5. **Test fix**:
   - Load a style with InOutHelper/InOutDelayX
   - Measure animation timing before and after fix
   - Verify no regression in frame rate
   - Confirm with visual inspection: animation should be smooth, not stuttering

6. **Performance validation**:
   - Re-run frame rate baseline from Task 3.1 after fix
   - Compare: baseline vs post-fix
   - If regression >5%: Investigate hot path overhead (see virtual call traces)

**Code Locations to Review:**

**Verify:**

### Task 3.3: Investigate & Fix Pre-Ignited Color Issue

**Objective:** Root cause why colors show before ignition triggered, implement initialization fix.

**Effort:** 1.5 hours
**Type:** Debug + Fix
**Depends on:** None (independent of Task 3.2)

**Actions:**

1. **Understand color initialization flow**:
   - Where does getColor() get called before run()?
   - Review ProffieOS main loop: Does it call getColor() before checking ignition?
   - Or is issue in RtColorNode subclasses not respecting ignition state?

2. **Identify the problem case** (if reproducible):
   - Which style/font combination shows pre-ignition?
   - Is it: all styles, greyscale fonts only, specific effect?
   - Review REQUIREMENTS.md UAT4 (greyscale font colors)
   - Hypothesis: Color nodes initialized without checking ignition state

3. **Review color node implementations** (lines 186-280):
   - RtRgb, RtRgba, RtMix, RtCompose, RtAlphaL, RtOverDriveWrap
   - Which node types can be affected? (All of them — any node can be at root)
   - Should color nodes check SaberBase::IsOn() before returning color?
   - Or should wrapper (e.g., RtAlphaL) handle ignition state?

4. **Check for ignition-aware wrappers**:
   - Is there already a wrapper that checks blade state?
   - Look for: blade->is_on(), SaberBase::IsOn() in color node code
   - If not: Should RtLayers/RtCompose check ignition before composing?

5. **Root cause hypothesis testing**:
   - Hypothesis A: Color returned at 100% alpha when ignition state = off
     - Solution: Check blade state before returning color
   - Hypothesis B: Alpha function not zeroing when ignition = off
     - Solution: Check RtAlphaL alpha calculation
   - Hypothesis C: Default color value wrong
     - Solution: Change default from current color to Black/Transparent

6. **Implement fix**:
   - Likely: Add blade state check to RtAlphaL or root color node
   - Pattern: `if (!blade->is_on()) return RGBA_um::Transparent();`
   - Alternative: Check IgnitionDelayBase state if available
   - Test: Load style with greyscale font, verify black before ignition

7. **Validation**:
   - Parse test style with known pre-ignition issue
   - Visually inspect: blade should be dark before ignition
   - Measure: frame rate impact of state check (negligible, <0.1%)

**Code Locations to Review:**
- RtAlphaL class (line 201)
- RtCompose class (line 211)
- RtMix class (line 225)
- RtColorNode base class (line 133)
- Blade state access patterns elsewhere in code

**Verify:**
- Root cause identified and documented
- Fix implemented and tested
- Pre-ignited color no longer appears

**Done:**
- Pre-ignited color issue resolved or documented as unfixable
- Test style loads and blade behavior correct
- No frame rate regression from state checking

### Task 3.5: Validate & Fix Return Value Semantics (Power Control)

**Objective:** Audit all Rt* class run() return types and values, fix any issues preventing blade power-off.

**Effort:** 1.5 hours
**Type:** Audit + Validation
**Depends on:** None

**Actions:**

1. **Understand return value contract** in ProffieOS:
   - What does BladeStyle::run() return?
   - What value means "blade can power off"? (false = off, true = keep on)
   - Or opposite: true = off, false = keep on?
   - Reference: blade_style.h, SaberBase, or ProffieOS documentation

2. **Review current Rt* implementations** (RtColorNode, RtFuncNode):
   - RtColorNode::run() signature (line 136: `void run(...)`)
   - RtFuncNode::run() signature (line 143: `void run(...)`)
   - Issue: Both return void, not bool!
   - This is likely a major problem (no power control possible)

3. **Root cause analysis**:
   - How do compiled styles return power control values?
   - Do they inherit from a base class that returns bool?
   - Can we add return values without breaking compatibility?

4. **Design options**:
   - **Option A**: Change RtColorNode::run() to return bool
     - Pro: Type-safe, follows ProffieOS pattern
     - Con: Requires refactoring all Rt* classes (~50 classes)
   - **Option B**: Add separate method (e.g., canPowerOff()) → bool
     - Pro: Non-breaking change
     - Con: Two separate methods to maintain
   - **Option C**: Store state variable, not return value
     - Pro: Minimal changes
     - Con: Less clean API

5. **Implement chosen design**:
   - If Option A: Create new run() signature, update all implementations
   - If Option B: Add canPowerOff() to all effect nodes
   - If Option C: Add `power_state_` member variable, update initialization/run()

6. **Validation**:
   - Load a style with time-limited effect (e.g., clash effect that fades)
   - Test: Blade powers off when effect ends
   - Compare: vs compiled style behavior (should match)
   - Measure: any performance impact from extra return checking

7. **Edge cases**:
   - What if style has no power-control mechanism? (Default to can power off)
   - What if multiple effects? (Blade stays on if any effect active)
   - What about transition states? (Should support mid-transition hold)

**Code Locations to Review:**
- RtColorNode base class (line 133)
- RtFuncNode base class (line 140)
- All Rt* implementations that override run()
- SaberBase / blade_style.h for power control pattern

**Verify:**
- Return value semantic design chosen and documented
- All Rt* classes updated to support return value
- Test: Blade power-off behavior correct

**Done:**
- Return value semantics fully implemented and working
- Blade powers off at correct times
- Test styles exhibit proper power control behavior
